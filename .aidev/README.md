# hivemind under AIDEV

AIDEV verifies changes to this repository through the slots in `project.yaml`,
integrates them into `aidev/integration`, and people merge that into `develop`
through merge requests (as in hive/HAfAH and hive/haf). GitLab CI doesn't run for
AIDEV branches (`ai/*`, `session/*`, pushes to `aidev/integration`); see
`.gitlab-ci.yml` `workflow:`.

## Suites

`.aidev/run-checks.sh <suite> <step>...` runs the named steps and writes
`test-results/<suite>/junit.xml`, one test case per step, with the step's log tail as
the failure body. `unit` also writes one case per test (`unit.xml`), `api-smoke` one
per call (`api-smoke.xml`), `tavern` one report per tavern group (`tavern-<group>.xml`).
A step that exits 77 is recorded as skipped, with the last line it printed as the reason:
its precondition belongs to the host environment, not to the change.

| Step | What |
|---|---|
| `unit` | pytest on `tests/utils` and `tests/steem`, those that exist (the Makefile's `test-utils` / `test-steem`), run from a scratch directory with `hive` imported from the checkout |
| `ruff` | `ruff check` and `ruff format --check` on `hive/`, `tests/` and `scripts/` with `pyproject.toml`'s configuration (ruff pinned in the image), excluding the `tests/tests_api` submodule |
| `install` | into the stack's HAF database as `haf_admin`, the way the hivemind image's `setup --with-apps` does it: `scripts/setup_postgres.sh`, the `reputation_tracker` and `hafah` submodules' `install_app.sh`, `scripts/install_app.sh`, then `hive build_schema` from this checkout; passes when `hivemind_endpoints` has functions |
| `reinstall` | `scripts/uninstall_app.sh`, then the hivemind half of `install` again |
| `mock-wrapper` | `.aidev/app_next_block_wrapper_check.sql`: applies `scripts/ci/wrapper_for_app_next_block.sql` (which `scripts/ci/add-mocks-to-db.sh` applies in CI's `sync` and the shared hivemind's seed) twice to the stack's HAF, in a transaction it rolls back, and checks that the 3-argument `hive.app_next_block` delegates to `app_next_block_haf`, that re-applying changes nothing, the 4999979 cap with HAF's range stubbed, and that `hive.get_estimated_hive_head_block` returns `hive.get_irreversible_head_block()` with HAF's original kept as `get_estimated_hive_head_block_haf` and its EXECUTE grants matched |
| `api-smoke` | `.aidev/hivemind_smoke.py`: PostgREST over the installed schema (as `scripts/start_postgrest.sh` starts it), then JSON-RPC calls to `/rpc/home` (`hive`, `condenser_api`, `follow_api`, `tags_api`, `bridge`, unknown API / method) and `GET /rpc/get_sync_status`, each checked against the shape an empty chain answers with |
| `tavern` | `.aidev/hivemind_tavern.py`: CI's tavern API suite against a per-run clone of the shared synced hivemind, with this tree's PostgREST SQL reloaded into it; see [The `tavern` step](#the-tavern-step) |

The install steps copy `scripts/`, `reputation_tracker/` and `hafah/` to a scratch
directory and write the submodules' `scripts/set_version_in_sql.pgsql` there
(`git rev-parse HEAD`, or `aidev` when the checkout has no usable git), because a
workflow checkout may have no `.git`. When the checkout has no `hive/_version.py`
(generated by versioningit at `pip install` time, gitignored) the checks write one.

An empty HAF has never seen hived, so the install steps first call
`hive.initialize_extension_data()`, which is what hived does when it first connects. It
fills `hafd.events_queue` and `hafd.hive_state`. Without `events_queue`,
`hive.is_instance_ready()` is false and hivemind's API refuses with "HAF instance is not ready"
(`get_sync_status`, which the smoke test waits on). A HAF older than hive/haf#354 also
needed `hive_state` filled, or `hive.app_register_table` skipped `hive_rowid` and
reputation_tracker's install failed with `child table is missing column "hive_rowid"`; the
pinned `2ae98b82` includes #354, so only the `events_queue` reason remains.

| Slot | Steps | HAF stack |
|---|---|---|
| quick | unit, ruff | no |
| coverage | unit | no |
| full | unit, ruff, install, reinstall, mock-wrapper, api-smoke, tavern | yes, and the shared hivemind |
| canary | unit, ruff, install, reinstall, mock-wrapper, api-smoke | yes |
| baseline | install, reinstall, api-smoke | yes |

`static` and `system` are unbound: AIDEV runs neither for a project.

Not covered yet: the python API client tests and the benchmarks. They stay in GitLab CI.

## The `tavern` step

`full` runs CI's tavern API suite (`tests/api_tests/hivemind/tavern/`) against the
[shared synced hivemind](#the-shared-synced-hivemind-sandboxsharedhivemind), which
`sandbox.external` names `hivemind` (`AIDEV_EXTERNAL_HIVEMIND_HOST` / `_PORT`).
`.aidev/hivemind_tavern.py`:

1. reads the tree's key (`shared-hivemind/shared_fixture.py`):
   - its **schema revision**: the last quoted 40-hex hash in
     `hive/db/sql_scripts/upgrade/update_db_patchlevel.sql`, the key CI's
     POSTGREST_ONLY path greps;
   - its **sync recipe**: a SHA-256 over the git blob ids of the tracked files that
     decide what a seed syncs besides the schema, as they are on disk
     (`scripts/ci/add-mocks-to-db.sh`, `scripts/ci/wrapper_for_app_next_block.sql`,
     `mock_data/`, `hive/indexer/`, `hive/utils/`, `hive/db/`,
     `scripts/install_app.sh` / `.sql`, `scripts/setup_postgres.sh`,
     `.aidev/shared-hivemind/seed.sh`), the `reputation_tracker` and `hafah`
     commits the tree pins, and `HAF_FIXTURE_COMMIT` from `project.yaml`.
     `hive/db/sql_scripts/postgrest/` and `endpoints/` (CI's
     `POSTGREST_ONLY_PATTERNS`) are left out: step 3 reloads them;
2. skips by name when the provider's clone API predates sync recipes (`serve.sh`
   installs `admin.sql` only when the service starts), else lists the provider's
   templates (`hivemind_shared.health()`, newest first) and
   takes the one seeded for both. **On a recipe miss** (the mocks, the indexer or an
   app moved without a patch-level bump) it calls
   `hivemind_shared.request_seed(<revision>, <recipe>, <HEAD commit>)` and uses the
   newest template of the revision instead, printing
   `advisory: no hivemind fixture for sync recipe <recipe> of schema revision <rev>;
   using <template>, synced by recipe <other>; seeding requested`. Its data is
   schema-compatible, so the run goes on, but a pattern that depends on what the
   recipe changed may disagree with CI's. **On a revision miss** (a schema or
   indexer change that bumped the patch level) it requests the seed the same way and
   skips with `no hivemind fixture for schema revision <rev>; seeding requested`.
   A missing fixture never fails the gate. The next run after the seed finishes
   (about 15–20 minutes) has it. The seed fetches that commit from GitLab, so it
   succeeds only for a pushed commit whose patch level yields the revision and whose
   recipe is the requested one (an uncommitted edit to a recipe file changes the
   tree's recipe, not the commit's); otherwise the request is marked `failed` in
   `hivemind_shared.seed_requests`;
3. clones it (`clone_run_database('tavern-<UTC time>-<random>', <revision>, <its recipe>)`) and
   reloads the tree's PostgREST SQL into the clone as `hivemind` with
   `scripts/ci/reload-postgrest-functions.sh` (what CI's POSTGREST_ONLY path does),
   so query changes are tested without a re-sync. The reload cannot install the
   admin-level scripts (`schema.py`'s `_setup_admin_runtime_code`, plpython3u):
   `hivemind` owns their schema, so it drops the template's copy, and the CREATE is
   refused with a warning, since only a superuser may create them. The step then
   installs the tree's copy through the provider,
   `install_admin_script('<run id>', <script>)`, which runs it as `haf_admin` in that
   run's database. On a provider whose clone API predates it, the step says so and
   runs without them and skips search-api;
4. serves the clone with PostgREST as `scripts/start_postgrest.sh` does, with
   `PGRST_DB_ROOT_SPEC=home` standing in for the postgrest-rewriter's `/` → `/rpc/home`;
5. runs every group of `.gitlab-ci.yml`'s `SMOKETESTS` list (read from that file,
   in its order) as `scripts/ci/start-api-smoketest.sh` does in
   `e2e_benchmark_on_postgrest`: `-m "not postgrest_ignore" --dist loadfile`, with
   `HIVEMIND_TAVERN_WORKERS` workers (default 4). Tox is not used, because the check
   container has no network to build its venv; the runtime image carries
   `[testenv:tavern]`'s pins instead. As in CI, `search-api_patterns` counts like
   every other group when the clone has the `pg_search` extension, and is not run,
   printing `skip search-api_patterns (<reason naming pg_search>)`, when it has none;
6. moves the `.out.json` files tavern writes next to the patterns to
   `test-results/full/tavern-out/` and drops the clone, also when the run fails. A
   clone a killed run leaves behind is reaped after 6 hours.

**Adding or refreshing a pattern.** Write the `.tavern.yaml` and a first
`.pat.json` (or change the SQL), run `aidev test run --slot full`, and read the
actual response from `test-results/full/tavern-out/<group>/…/<test>.out.json`. When
it is right, copy it over the `.pat.json`. Run the slot again: the group's
`tavern-<group>.xml` must pass. The clone holds CI's data (5M blocks, the mocks,
sync to 5000024), so patterns produced this way match CI's `e2e_benchmark_on_postgrest`.
A change that alters synced data gets a fixture only once the commit bumping the
patch level is pushed. Until then the step skips by name, and CI's sync job is the check.

### Positive tavern patterns

A worker can't produce the values of a new positive pattern: they come from CI's
mock-data database. It commits the new `*.tavern.yaml` with a `{}` placeholder
`.pat.json` and names those tests in its summary. After the workflow, an operator with
`GITLAB_TOKEN` and push access runs `scripts/ci/generate_patterns.py` (see `CLAUDE.md`,
"Tests that need real data"): it pushes the commit to a scratch branch
`patterns/<shortsha>` with `-o ci.skip` (AIDEV's `ai/*` and `session/*` branches run no
pipeline), runs a pipeline on a cached sync (`POSTGREST_ONLY_CHANGE=true`,
`AUTO_SKIP_SYNC=false`), copies the `.out.json` files of `e2e_benchmark_on_postgrest`'s
artifacts to the placeholders, prints a summary per test, and deletes the branch.
`--dry-run` prints the branch, variables and tests without pushing. Check the values
against independent data before committing them. If the operator step isn't available,
the worker files a follow-up issue for the patterns.

## Quality evaluation

AIDEV's quality evaluation runs its own collectors except where `project.yaml`'s
`quality:` section declares the project's command for a stage. `typecheck` is declared:
`.aidev/mypy_sarif.py hive` runs mypy at its default strictness (unannotated functions
aren't checked, imports without stubs are ignored) and prints SARIF, because AIDEV's own
collector runs `mypy --strict` on every changed file, which no change to untyped code here
could pass. Findings on lines a change doesn't touch are advisory.

## The HAF test stack (`test-stack.compose.yml`)

One service, `haf`: the HAF testnet image for HAF develop commit `2ae98b82`, started
empty with the `sleep_infinity` maintenance script. The checks reach it as `haf` on the
stack's network. CI's `find_haf_image` tracks HAF `develop` (the common-ci-configuration
template's default `UPSTREAM_BRANCH`; hivemind no longer overrides it), so the commit it
resolves moves with HAF. When it does, re-pin both HAF pins together, to the same commit:
the image digest here to `registry.gitlab.syncad.com/hive/haf/testnet:<commit, 8 chars>`,
and `HAF_FIXTURE_COMMIT` / `HAF_FIXTURE_DIGEST` in `project.yaml` to
`registry.gitlab.syncad.com/hive/haf/fixture-5m:<commit, 8 chars>` (see
"Changing the HAF version" under the shared synced hivemind below).

To run the stack checks by hand (with the submodules checked out):

```bash
docker compose -p hivemind-checks -f .aidev/test-stack.compose.yml up -d --wait
docker run --rm --user "$(id -u):$(id -g)" --network hivemind-checks_default -v "$PWD:/w" -w /w \
    "$(grep -o 'registry[^"]*aidev-tests@sha256:[0-9a-f]*' .aidev/project.yaml)" \
    .aidev/run-checks.sh full unit install reinstall api-smoke
docker compose -p hivemind-checks -f .aidev/test-stack.compose.yml down -v
```

## The shared synced hivemind (`sandbox.shared.hivemind`)

A persistent PostgreSQL that holds HAF's 5M replay with hivemind installed, mocked
and synced the way CI's `sync` job does it. It keeps frozen templates keyed by
(hivemind schema revision, sync recipe) (see [The `tavern` step](#the-tavern-step))
and gives each test run, from any session, its own copy-on-write clone of one. It is declared under `sandbox.shared.hivemind` in `project.yaml`,
defined in `shared-hivemind.compose.yml` and implemented in `shared-hivemind/`,
modelled on hive/haf's `shared-haf` service. A dedicated session hosts it:

```bash
aidev session create hivemind-shared --host steem-13 --remote git@gitlab.syncad.com:hive/hivemind.git \
    --target-branch aidev/integration --shared-service hivemind
```

**Create it as soon as this declaration lands.** While no session serves
`hivemind/hivemind`, AIDEV refuses this project's slots that start a stack (`full`,
`canary`, `baseline`) as `service_stack_unavailable`, naming the provider. That is
never a failed test, but it is no verdict either. A remotely executed run reads the
declaration for every slot, so it refuses there too.

Consumers declare `sandbox.external: [{name: hivemind, provider: "hivemind/hivemind"}]`,
connect to `$AIDEV_EXTERNAL_HIVEMIND_HOST:$AIDEV_EXTERNAL_HIVEMIND_PORT` as
`hivemind_shared_consumer` (no password, no secret), and per run:

```sql
-- in database hivemind_shared
select * from hivemind_shared.health();  -- revision, recipe, template, HAF and hivemind commits, head block, live clones
select hivemind_shared.clone_run_database('<run id>', '<revision>', '<recipe>');
    -- returns run_<run id>, cloned from the newest template matching both; null = any
select hivemind_shared.install_admin_script('<run id>', '<script>');
    -- runs an admin-level script (plpython3u) as haf_admin in run_<run id>; refuses any other database
select hivemind_shared.drop_run_database('<run id>');                 -- when done
select hivemind_shared.request_seed('<revision>', '<recipe>', '<40-hex commit>');
    -- seeded | pending | seeding | done | failed
select * from hivemind_shared.seed_requests;                          -- what the seeder is doing, failures' log tails
```

A run id is 1-48 of `[a-z0-9_-]`, a recipe 64 hex digits
(`shared_fixture.py recipe tree <checkout> <HAF commit>`). `clone_run_database`
raises `no_data_found` when no template matches. A template seeded before the recipe
joined the key is listed with recipe `unrecorded`, which no tree matches. Inside `run_<id>` a run connects as `hivemind`, the role that
owns hivemind's schemas, to reload SQL and serve PostgREST.

**Access.** Over TCP only from the fleet's LAN, without a password, as on the shared
HAF: `hivemind_shared_consumer` reaches only `hivemind_shared` and `run_*` databases,
and `hivemind` only `run_*` databases. The LAN is `192.168.3.0/24`, `192.168.5.0/24`,
`192.168.6.0/24`, plus `172.16.0.0/12` for the provider host's own connections through
docker's NAT. The data is public chain data plus CI's mocks. `127.0.0.1` (trusted for
every role) is the `hivemind` container's own network namespace, shared only with
`seeder`.

**How it works.** Three services:

- `cluster` (one-shot, the `hive/haf/fixture-5m:<commit>` image for the HAF commit
  the test stack pins) refuses a data root that is not ZFS. On the first start of a
  HAF commit it copies the image's replayed cluster to
  `$HIVEMIND_SHARED_DATA_ROOT/<commit>/haf_db_store`, as hive/haf's `seed.sh` does.
- `hivemind` (same image) bind-mounts that directory at the image's own
  `haf_db_store` path. `start.sh` sets `file_copy_method = clone`. `serve.sh` installs
  the clone API (`admin.sql`) into `hivemind_shared` and, once per HAF commit, freezes
  `haf_template` from `haf_block_log`. It then reaps run databases older than
  `HIVEMIND_SHARED_RUN_TTL` (6 hours) every 5 minutes, along with `run_*` databases no
  run is registered for.
- `seeder` (this project's runtime image, which has hivemind's Python dependencies,
  psql and git) shares `hivemind`'s network namespace. `seeder.sh` takes pending
  `seed_requests` one at a time. Every 30 minutes it also requests a seed for the tips
  of `HIVEMIND_SHARED_SEED_REFS` (`develop aidev/integration`) by their revision and
  recipe (`shared_fixture.py recipe commit`), so they are seeded before anyone asks,
  also when only the recipe moved. `seed.sh <revision> <recipe> <commit>`:
  1. fetches that commit, with the `reputation_tracker` and `hafah` submodules, from
     `HIVEMIND_SHARED_REMOTE` (gitlab.syncad.com/hive/hivemind) and checks its patch
     level yields the revision and its recipe on `HAF_FIXTURE_COMMIT` is the recipe;
  2. clones `haf_template` into `seed_<revision>_<recipe, 12 hex>`;
  3. runs what CI's `sync` job runs (`docker/docker-compose-sync.yml`):
     `setup_postgres.sh`, the submodules' `install_app.sh`, `scripts/install_app.sh`,
     `scripts/ci/add-mocks-to-db.sh`, `hive build_schema`, then reputation_tracker's
     `process_blocks.sh` alongside
     `hive sync --test-max-block=5000024 --community-start-block 4998000 …`,
     with the same flags, from the fetched source;
  4. checks hivemind reached block 5000024, renames the database
     `hivemind_<revision>_<recipe, 12 hex>`, freezes it (`is_template`, no
     connections) and records it.

  CI's `ALTER SYSTEM` tuning (`fsync = off`, …) is left out: it would apply to a
  cluster serving live clones, and it changes no synced data. A failed seed is marked
  `failed` with its log tail and is retried only when a different commit is requested.

  **Retention.** Whenever it is idle, the seeder keeps the newest
  `HIVEMIND_SHARED_KEEP_TEMPLATES` (3) templates of each revision and drops the older
  ones that no registered run was cloned from (`shared_fixture.py retire`,
  `hivemind_shared.drop_template`); one still cloned from goes once its runs are
  dropped or reaped. A request whose template was retired is queued again by the next
  `request_seed` for it.

As for the shared HAF, the `shared-hivemind/` bind reads the checkout through
`${AIDEV_HOST_CHECKOUT}`, because compose runs in the session worker against the
host's daemon.

**Host setup (once, on steem-13).** The data root must be a dataset on a pool with
`feature@block_cloning` (ZFS 2.4+). No credential is provisioned.

```bash
sudo zfs create haf-pool/aidev-shared-hivemind       # mounted at /haf-pool/aidev-shared-hivemind
```

**Changing the HAF version.** Set `HAF_FIXTURE_COMMIT` and `HAF_FIXTURE_DIGEST` in
`sandbox.shared.hivemind.env` to the `hive/haf/fixture-5m` image of the commit
`test-stack.compose.yml` pins (hivemind's own HAF, which may differ from what hive/haf's
`sandbox.shared.haf` pins). The next
start copies that commit's cluster, and the seeder re-seeds the refs' revisions in it.
The old commit's directory under the data root can then be destroyed. **Changing the
runtime image** (`environment.image`): re-pin `HIVEMIND_RUNTIME_IMAGE` to the same digest.

## The test runtime image (`runtime/`)

The checks run in a container with your uid: `python:3.14-slim-bookworm` (the base of
this project's own `Dockerfile`) with `postgresql-client` and `git`, the `postgrest`
binary of `common-ci-configuration/postgrest` (the `POSTGREST_VERSION` of
`Dockerfile`), `create_haf_app_role.sh` / `common.sh` from common-ci-configuration at a
pinned commit (where `scripts/setup_postgres.sh` looks before it downloads them), and
`setup.cfg`'s `install_requires` plus pytest, ruff and mypy, and `tox.ini`
`[testenv:tavern]`'s deps (tavern, pytest-xdist, deepdiff, jsondiff) for the `tavern`
step and the shared hivemind's seeder. Every base and download is pinned.

When `runtime/Dockerfile` or `setup.cfg` changes, rebuild and re-pin **in the same
commit**:

```bash
.aidev/runtime/build.sh --push   # registry digest if aidev-<input hash> exists, else build + push
# put the printed repo@sha256:<digest> into project.yaml environment.image
# and sandbox.shared.hivemind.env.HIVEMIND_RUNTIME_IMAGE
```

To build through a pull-through registry cache near the build host, set
`AIDEV_IMAGE_CACHE_BY_REGION` to `region=host:port` pairs, e.g.
`eu=cache.example.org:5001,*=cache2.example.org:5001`: a pair applies when its region is
a label of the host's FQDN, and `*` applies to any other host. Unset, the image is built
straight from `registry.gitlab.syncad.com`.
